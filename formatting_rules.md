# Formatting Rules

These formatting rules apply to all outputs: emails, Salesforce artifacts, call prep materials, meeting notes, etc.

## Default: Markdown Format

**All content is written in markdown** for use in Obsidian unless specified otherwise.

- Use standard markdown syntax:
  - **bold** for emphasis
  - *italic* for secondary emphasis
  - `code` for technical terms, API names, product names
  - ## headers for sections
  - - bullet lists
  - [link text](URL) for documentation links

## Critical: No Long Dashes

- **NEVER use long dashes (em dashes —)** - they look AI-generated
- Always use regular hyphens (-) instead
- Example:
  - ❌ "This is important — very important"
  - ✅ "This is important - very important"

## Exception: RFX Answers - Plain Text Only

**RFX answers must be plain text** (no markdown) since they go into forms/documents:
- No **bold**, *italic*, `code`, ## headers, or [links](url)
- Write out URLs directly: https://www.twilio.com/docs
- Use only: spaces, tabs, newlines, hyphens (-), regular text
- Use dashes (-) for bullets, tabs for indentation

## Email-Specific Rules

- Use markdown for structure and readability
- No signature (Gmail adds it automatically)
- No greeting unless it flows naturally
- Brief, clear, technical tone
- Link-centric: provide [documentation links](URL), don't write long explanations

## Salesforce Artifacts-Specific Rules

- Use markdown format (for Obsidian)
- Three sections: ## USE CASE, ## RISKS, ## NOTES
- Use markdown bullets and formatting
- Keep it concise and scannable

## Call Prep Materials

- Use markdown format (for Obsidian)
- Use ## headers for sections
- Use **bold** for key metrics, dates, names
- Use `code` for product names, API names
- Use bullet lists for structure
- Include links to relevant resources

## General Voice

- Concise and clear
- Technical but accessible
- No fluff or filler
- Focus on "why" not just "what"
